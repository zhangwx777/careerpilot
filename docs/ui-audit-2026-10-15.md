# CareerPilot UI 审查（2026-10-15）

审查分支：`feature/2026-10-15`。

范围：保留现有整体风格，检查 UI 架构、信息层级、排版和响应式表现。审查阶段未修改应用代码；后续修复和验证记录见文末。

## 结论与保留项

现有界面已具备统一的视觉基础：冰蓝背景、白色半透明面板、蓝色主操作、圆角控件和 Phosphor 图标。导航按总览、记录、分析、工作区分类，页面职责基本清晰。建议在这套语言内做局部修正。

应保留现有配色、Logo、图标体系、主要导航与路由，以及原始资料和分析结果的职责划分。现有键盘焦点、减少动画偏好、原生确认对话框也值得保留。

本次采用 frontend-design 的层级、文字和布局原则，以及 design-taste-frontend 的保留式审查流程。后者明确不以密集工作台和数据表格为适用对象，因此未套用其营销页面的版式、动效或图片要求。

## 验证方式与边界

- 检查 React 页面、共享组件、全局样式、桌面窗口约束和现有 UI 回归测试。
- 实际浏览了求职总览、投递台账、求职地图（月历）、新增投递、智能录入、面经工作台、备战中心和模型设置。
- 使用临时只读样例 API，包含十个有数据的投递阶段、长岗位名、日程、模型配置等；没有读取真实求职数据，也没有调用模型。
- 检查窗口宽度：1440、1280、1180、1080、1024、820 和 390px；并非每个页面都逐一覆盖所有尺寸。
- 桌面窗口最小宽度为 1080px（`desktop/main.cjs:554`）。820px 和 390px 的问题属于浏览器窄窗口或移动布局；1180px 和 1080px 的问题也会影响桌面端。
- `node --test frontend/ui-regressions.test.ts`：17 项通过。这些主要是源码匹配测试，不能证明真实布局没有溢出。
- 未验证真实生成过程、已填充的备战报告与练习详情、Electron 更新入口或完整键盘可访问性；本报告不对这些场景作通过结论。

## 优先修复：实际布局问题

### 1. 投递台账的操作列在部分桌面宽度下被裁切

证据：1280px 下“编辑”“删除”已经挤成竖排；1180px 下操作列落在容器边界外，被 `.ledger { overflow: hidden }` 裁掉。样例实测容器右边界约为 1129px，操作区右边界约为 1239px。

原因：五列 Grid 的最小列宽、间距和内边距需要约 976px，但 1180px 窗口扣除侧栏和页面边距后仅剩约 849px。当前只在视口不超过 1100px 时切成紧凑布局，切换偏晚。

建议：按内容区域实际宽度触发紧凑布局，或提前采用现有紧凑行结构。保证操作始终可见，操作文字不逐字换行；长岗位名应提供可读全称的方式。

定位：`frontend/src/styles.css:269`、`:271`、`:279`、`:300`、`:1028`；`frontend/src/pages/ApplicationsPage.tsx:166`。

验收：1180px、1280px 下编辑和删除完整可见；长岗位名称不挤占操作区域；1100px 两侧切换不出现布局断层。

### 2. 月历与当天详情的双栏宽度下限过高

证据：1180px 窗口下，月历布局需要 620 + 320 + 20 = 960px，可用区域约 849px，页面出现横向滚动，详情面板越过右侧边界。1080px 桌面最小宽度下，工作区 clientWidth 为 821px、scrollWidth 为 990px，同样溢出。

原因：`.calendar-layout` 的两列有固定最小值，但直到 760px 才改成单栏。

建议：在双栏容纳不下时，将当天详情排在月历下方；更宽窗口继续保持现有双栏。不需要缩小日期文字或压缩七列月历来硬塞内容。

定位：`frontend/src/styles.css:458`、`:1052`；`frontend/src/pages/TimelinePage.tsx:251`。

验收：1080px、1180px 下没有非预期横向滚动；选中日期后当天详情完整可达。

### 3. 新增投递的说明栏在浏览器窄窗口下占比过大

证据：820px 下仍保留 244px 侧栏和至少 240px 的表单说明列，实际输入框仅约 184px 宽。输入提示被截断，正文区域比辅助说明区域还窄。

原因：`.form-grid` 直到 760px 才切为单栏，缺少中间宽度的处理。

建议：先让说明栏换到表单下方，或把短说明收进表单中的辅助区域，再根据内容宽度决定是否使用双栏。保留字段顺序。

定位：`frontend/src/styles.css:326`、`:1052`。

验收：820px、1024px 下字段有合理宽度；辅助说明不抢占主要录入区域。

## 建议优化：信息与操作层级

### 4. 总览应优先帮助用户看到下一步行动

证据：十个阶段有数据时，投递分布卡明显变高；右侧“当前关注”因 `align-items: stretch` 被拉成同高，产生大面积留白。在 1280×720 下，“接下来”落到首屏底部附近；390px 下该区顶部约在 1246px。

建议：保持现有面板外观，给摘要和分布更紧凑的排版；优先展示当前关注和接下来行动。手机上尤其应避免让全部阶段分布和三个纵向统计块排在行动列表前面。

定位：`frontend/src/styles.css:412`、`:451`、`:1112`；`frontend/src/pages/DashboardPage.tsx:80`。

这属于体验取舍，并非所有数据量下都会出现的问题。调整时应保留全部阶段信息的可达性。

### 5. 模型设置页可以减少重复标题和配置前置说明

证据：1440×900 的首屏已经包含“模型分工”“供应商与连接参数”“已配置模型”“连接参数”及能力条，但只看到实际字段的开头，保存操作还在下方。

建议：把供应商选择与已配置项组织成同一个配置切换区域，减少重复的标题层级；能力信息继续保留但降低视觉权重。对长表单，可考虑仅在编辑期间显示就近的保存操作。保留字段顺序及现有能力说明的内容。

定位：`frontend/src/pages/SettingsPage.tsx:230`、`:244`、`:252`、`:279`、`:307`。

### 6. 阶段轨道需要更容易理解，长名称需要完整阅读入口

证据：阶段轨道由九个无可见文字的节点组成，各节点名称依赖鼠标悬停 `title`；当前状态同时出现在下拉框中。长岗位名称在台账里单行截断，但没有完整名称的提示或展开入口。

建议：保留轨道外观，为当前阶段增加清晰的文字关联，避免要求用户记住每个点代表什么；给被截断的岗位名提供详情、展开或适当的全称提示。不要为此重复增加一整排九个阶段标签。

定位：`frontend/src/components/StatusRail.tsx:15`；`frontend/src/pages/ApplicationsPage.tsx:144`。

### 7. 移动导航的后半部分不易发现

证据：390px 下，顶部八项导航总宽约 778px，容器宽约 342px。面经、备战、简报、设置需要横向滚动才能看见。

建议：保留导航名称和路由，补充明确的横向可滚动提示，确保当前项可见；如果后续确实投入移动使用，再评估折叠菜单。无需立即增加另一套导航体系。

定位：`frontend/src/components/Layout.tsx:61`；`frontend/src/styles.css:1061`。

## UI 架构的轻量整理空间

现有 React Router + Layout + 页面组件的分层足够支持当前规模，Radix Themes 与自定义样式也可以继续使用。主要问题在样式职责和公共排版约束，暂不需要引入新的组件库或通用页面配置框架。

1. **统一少量公共排版单元。** 页面标题区、字段提示、空状态和面板标题重复出现在各页面，可在实际修复时按需复用。`DesignPrimitives.tsx` 当前只提供 StatusBadge 和 ContextBar，没有必要一次性把所有页面都抽象成组件。
2. **让 Token 真正生效。** `--space-*` 和 `--text-*` 已定义，但目前没有在该样式表中被引用；正文还引用了未定义的 `--ink-soft`。优先统一字号、行高和辅助文字颜色，保持现有字体与画风。
3. **按组件收拢覆盖规则。** 同一 `.intel-context` 的 padding 被后面的 `.context-bar` 改写；设置页和末尾统一表面样式也有覆盖关系。不是样式文件长度本身有问题，而是一个组件的最终效果需要跨多处追踪。可以在触及相关组件时收拢其默认、变体和断点规则。
4. **保留一个页面级 main。** Layout 已提供 main，Intel 和 Practice 页面内部仍使用 main。内部区域宜使用 section 或 div，保持页面地标清晰；这是语义整理，不改变视觉。
5. **补能发现本次问题的浏览器断言。** 当前 17 项 UI 测试通过，但裁切仍能实际复现。修复时重点验证操作区位于可见容器内、页面无非预期横向溢出，以及长文本和多阶段数据下的布局，而非只匹配 CSS 字符串。

建议实施顺序：先修台账与月历的桌面问题，再处理表单中间断点；之后优化总览首屏和设置页层级，最后随相关改动整理公共样式。
