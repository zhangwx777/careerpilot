# 产品需求文档（PRD）

## 1. 产品定位

面向秋招、春招等校园招聘场景中个人求职者的**求职作战台**。不做自动投递，专注**信息聚合与决策辅助**：把分散在各平台的投递进度、时间线节点统一成一张作战地图，并针对目标岗位聚合结构化面经情报。

优先满足个人自用，体验完善后再考虑产品化。

## 2. 背景与问题

国内校园招聘与海外求职结构不同，海外工具（海投、ATS 优化、Easy Apply）的核心假设在国内并不完全成立。真正的痛点：

- **多平台进度分散**：网申官网 + 牛客 + 各公司小程序，状态更新不同步，全靠手动追。
- **时间线密集**：大厂 HC 8 月集中释放、10 月中旬基本关闭，窗口约 6 周，错过节点 = 错过一年。
- **笔试/面试冲突**：多场笔试撞车、临期节点无人提醒。
- **面经碎片化**：牛客/小红书/微信群到处是，无法针对"我投的这家这个岗"聚合。

市面现状：自动投递、简历 ATS 优化、通用模拟面试均已饱和且部分为国内伪需求。本产品切入未被做好的空白点。

## 3. 目标用户

- 主要：正在参加秋招、春招等校园招聘的应届生 / 实习生（当前为作者本人自用）。
- 特征：同时投递多家、需要统一管理进度与时间线、希望针对性准备面试。

## 4. 核心功能

### 4.1 方向 A：进度指挥中心

| 功能 | 说明 | 优先级 |
|---|---|---|
| 投递记录管理 | 公司 / 岗位 / 投递记录的增删改查 | P0 |
| 状态机 | 已投递 → 笔试 → 一面 → 二面 → 三面 → HR面 → offer / 挂 | P0 |
| 半自动解析 | 粘贴笔试/面试通知邮件、短信、网页文本，AI 抽取「公司+岗位+节点类型+时间」，人工确认后写入时间线 | P0 |
| 作战地图 | 时间线的日历视图 + 列表视图 | P1 |
| 冲突检测 | 检测两场笔试/面试时间撞车、临期未处理节点并提醒 | P1 |

### 4.2 方向 B：定向面经情报

| 功能 | 说明 | 优先级 |
|---|---|---|
| 面经聚合 | 针对某条投递（公司+岗位），聚合公开面经 + 用户粘贴内容 | P0 |
| 多源交叉验证 | 同一维度多个说法按时间新旧 + 来源数量加权，消解冲突 | P0 |
| 结构化情报 | 输出：几轮面试 / 常考题型 / 考察重点 / 最新面经摘要，可溯源，带置信度 | P0 |
| 备战规划 | 结合简历 + JD + 面经情报，生成能力差距分析 + 分解到日的备战任务，写回时间线 | P1 |

### 4.3 每日巡检（P2）

定时扫临期/冲突节点、对 pipeline 公司搜新面经、生成当日简报，避免重复提醒。

## 5. 关键产品原则

- **不做自动投递**：反爬/封号风险高、已饱和。
- **数据获取半自动**：粘贴文本 → AI 解析，不自建爬虫（合规 + 稳定）。面经允许 AI 主动联网搜索公开内容作为补充。
- **人工在关键节点介入**：解析结果、情报冲突由用户确认，不盲目自动写库。

## 6. 数据来源策略

- 投递进度、时间线：用户粘贴邮件/短信/网页文本，AI 解析。
- 面经情报：用户提供来源链接/粘贴内容 + AI 主动联网搜索公开面经。

## 7. 范围外 / 暂缓

- 定向模拟面试（红海，差异化需靠面经+简历驱动出题）：A+B 闭环跑通后再评估。
- 自动投递、简历 ATS 关键词优化。
- 多用户、账号体系、云端部署：产品化阶段再做。

## 8. 待定项

- 目标公司/岗位规模上限：待定。
- 面经数据源具体接入哪些站点：待定。
- 前端 UI 风格与交互细节：待定。
- 提醒渠道（仅站内 / 是否推送）：待定。
