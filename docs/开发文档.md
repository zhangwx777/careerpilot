## 3. 数据模型

主关系为 company 1—n position 1—n application 1—n (timeline_node / interview_intel)。公司和岗位是内部归档模型：创建投递时由 `company_name`、`position_title` 和可选 `jd_text` 自动查找或创建，前端不要求用户预先维护岗位库。面经按 `position_id` 聚合，录入时保存人工选择的轮次；每份材料和每个截图来源独立保留。第 3 期新增 `parse_session`，它记录一次通知解析和对应的 LangGraph 线程；确认后可一对一关联一个 `timeline_node`。

### interview_intel（面经情报）
| 字段 | 类型 | 说明 |
|---|---|---|
| id | int PK | |
| application_id | FK→application, cascade | |
| title | str | 自动生成的材料名称 |
| round_type | str | 测评/笔试/AI面/一面/二面/三面/HR面/多轮综合/未注明 |
| provider | str | 生成该材料的模型 provider |
| payload | JSONB | 结构化情报（几轮/题型/重点等） |
| confidence | float, 可空 | 置信度 |
| sources | JSONB | 来源列表 |
| created_at | datetime | |

面经资料按 `position_id` 聚合，因此同一岗位的多次投递和多次录入都保留为独立材料。工作台的“面试洞察”跨轮次分析全部来源：高频按语义考察方向聚合，并要求至少两个独立来源；核心问题和准备重点由岗位级洞察生成。“面经档案”只负责原文、截图识别文字、来源和单份材料抽取结果的追溯，不显示岗位级高频。

录入时 `round_type` 必填。手动文本、每张截图和每个联网页面都是独立来源；选择“多轮综合”时才允许模型为问题补充轮次，选择“未注明”时不猜测。岗位洞察按独立来源数统计考察方向，同一来源内的重复问题只计一次；只有一个来源时仍可生成核心问题，但明确显示尚未形成多来源高频方向。

| source_ids | JSONB | 回答引用的岗位面经来源 |
| created_at | datetime | |

### intel_session（面经聚合会话）
保存 LangGraph 的 `thread_id`、投递、抽取 provider、人工选择的 `round_type`、用户粘贴内容、分图识别文字、聚合草稿、冲突、状态和最终 `interview_intel_id`，以及加密的 `llm_snapshot` 和 `prompt_version`。它让人工裁决能在服务重启后恢复；只有裁决或无冲突完成后才写入 `interview_intel`。

`planner_session` 同样保存创建时的简历、JD、面经、provider、加密模型快照和提示词版本；`intel_chat_message` 为 assistant 消息保存相同快照。快照只进入数据库或 LangGraph 的密文状态，服务重启或修改默认模型不会改变已创建任务的配置。

### 第 5 期表

- `resume_profile`：仅一条本地简历档案（固定 id=1），保存提取文字和文件名，不保存原文件。
- `planner_session`：一次备战分析的简历/JD/面经快照、草稿、状态和 `thread_id`；新会话完成后直接保存分析结果，不再要求时间安排。`GET /api/planner-sessions` 默认返回全部历史，前端在备战中心展示并可重新打开。
- `preparation_task`：一个确认后的备战任务，关联 Planner 会话、投递和唯一的时间线节点；任务状态会同步该节点状态。
- `daily_briefing`：每个上海日期最多一份 JSONB 简报，记录临期/冲突、当日任务、增量来源和搜索失败信息。
- `reported_source`：已在简报中报告过的公开 URL，URL 全局唯一，用于跨日去重。

枚举定义集中在 `app/models.py` 顶部常量（`APPLICATION_STATUS` / `NODE_TYPE` / `NODE_STATUS`）。

## 4. 多模型 provider 层

### 设计
- `registry.py`：维护四家 provider 的名称和统一调用参数。`config_store.py` 只读取设置页保存的数据库配置；删除 Provider 配置后不会回退 `.env`。
- 数据库 API Key 和任务配置快照使用 Fernet 加密；LangGraph 状态只保存密文，调用前由后端解密。开发环境使用项目根目录 `.llm_config_secret`，桌面应用使用 `CAREERPILOT_DATA_DIR` 下的密钥，并兼容旧安装目录的密钥。密钥失效时 Provider 列表逐项标记“验证失败”，允许用户重新填写 API Key，不会让整个设置 API 失败。
- `provider.py`：`chat(messages, provider, response_format=None, config=None)` 统一入口。调用时显式指定 provider；调用错误会转换为不含密钥的认证失败、超时、服务不可用或响应异常。
- 结构化请求统一启用 LiteLLM 的 `drop_params`，并在兼容网关明确拒绝可选参数时有限重试；推理模型不再被强制传入不支持的 `temperature=0`。网页连接测试复用这套参数策略。
- `prompts.py` 和 `structured.py` 集中管理带版本的提示词、JSON 清理、Pydantic 校验和一次有限修复；流式问答收集完成后也复用该契约，原始用户文本、JD、面经和联网内容均视为不可信输入。
- 前端“分析模型”下拉读 `GET /api/providers` 的脱敏状态；设置页可保存、测试、删除覆盖并设置全局默认。创建任务时可传 provider，未传则使用全局默认。
- 设置页通过 `POST /api/llm/providers/{provider}/models` 读取当前 Key/Base URL 可用模型，不落库；Base URL 可填写供应商 API 根路径或兼容网关根路径，后端会规范化 `/models`，必要时尝试 `/v1/models`。

### 模型命名
设置页返回的模型 ID 原样保存；兼容网关若返回带 provider 前缀的 ID，不要手动重复添加前缀。

## 7. 启动器与网络排查

根目录 `start.bat` 只是 ASCII 包装器，实际逻辑在 `start.ps1`：先幂等初始化数据库，再启动后端和 Vite，并等待健康检查通过。每次运行都会获取一组新的项目端口，避免更新代码后误连旧进程；端口被其他程序占用时会顺延，因此不能假设浏览器地址永远是 5173。自动打开浏览器失败只显示警告，手动打开脚本打印的 Frontend 地址即可。

若“测试连接”和“读取模型”同时提示模型服务不可用，而浏览器能打开 Base URL，优先检查 Windows 防火墙或代理是否只允许浏览器、禁止 `backend\\.venv\\Scripts\\python.exe` 出站访问；其次确认网关提供 `GET /models` 或 `GET /v1/models`。认证失败、HTTP 404 和网络不可达在 API 中会分别转换为安全的用户提示，完整异常只应在本地调试日志中查看，不能复制 API Key 到日志或工单。

| POST | /api/planner-sessions | 创建岗位备战分析会话 |
| GET | /api/planner-sessions | 读取备战分析历史；可传 `status` 筛选 |
| GET | /api/planner-sessions/{id} | 读取后台分析进度和结果 |
| POST | /api/planner-sessions/{id}/confirm | 兼容历史待确认会话；新的备战分析不进入排期确认 |
| POST | /api/planner-sessions/{id}/discard | 丢弃历史待确认 Planner 会话 |
| GET | /api/preparation-tasks | 分页读取备战任务，可按投递、状态筛选 |
| PATCH | /api/preparation-tasks/{id}/status | 更新备战任务及关联时间线状态 |
| POST | /api/daily-briefings/run | 手动运行当天简报，重复调用返回同一份 |
| GET | /api/daily-briefings | 分页读取简报历史 |
| GET | /api/daily-briefings/{id} | 读取一份简报 |

所有列表使用 `page` / `page_size` 分页，`page_size` 最大 100。`offer` 和“挂”为终态；未结束状态可跳到任意后续阶段或转“挂”。删除公司/岗位依赖现有外键级联删除下属数据。

解析会话只有“待确认”时可确认或丢弃；相同终态操作幂等，互斥终态操作返回 409。确认页默认创建一条新投递；只有用户明确选择“关联已有投递”时才复用该记录，唯一匹配的候选仅作预选。AI 提取到相对工作日截止期限时，前端会根据开始时间计算结束时间；未提取到开始时间时默认当前时间。时间范围采用左闭右开 `[start, end)`。

前端以“职航 CareerPilot”为对外名称，进入系统的落地页是求职总览（`/dashboard`）：聚合全部投递数、各阶段当前分布与需要关注（冲突/临期/逾期）的待处理节点。此外包含投递台账、智能录入、求职地图、面经情报、备战中心、每日简报和模型设置，采用冷白背景、蓝灰边框与钴蓝强调色，减少装饰性卡片和渐变。投递台账按“公司 / 岗位”平铺展示，每条投递只显示一次公司和岗位；公司库、岗位库不再作为前端导航入口，但后端模型和管理 API 仍作为投递内部归档及其他业务链路的基础。新增投递直接填写公司、岗位和可选 JD；未提交内容用浏览器 `localStorage` 暂存，成功保存后清除。投递台账会给缺少 JD 的投递打标记；编辑投递时可直接把点错的当前阶段修正到任意阶段（台账里的推进仍只能向后）。智能录入按“原文输入 → AI 提取 → 确认写入”的顺序呈现：AI 只给候选，用户确认是新投递还是同一次既有投递后写入；时间线默认定位到当前日期，并提供列表和周一开始的月历，当日详情显示状态、冲突、临期和逾期提示。备战中心在首页展示历史分析，可打开已完成结果并新建分析，简历卡片支持替换和删除，历史分析使用创建时快照。面经问答历史使用固定高度的独立纵向滚动区，并保留可见滚动条。模型设置可根据 API Key 与 Base URL 读取供应商模型目录，用户从列表选择模型。

## 9. LangGraph 使用规划（第 3 期起）

仅在控制流本身需要图编排处使用，非装饰：
- 半自动解析的人工介入：`START → extract → review_interrupt → persist → END`。`extract` 按任务快照调用用户选择的 provider，使用集中式结构化输出契约，未知字段为 `null`；`review_interrupt` 的第一项操作是 `interrupt()`；PostgreSQL checkpointer 让进程重启后仍可用同一 `thread_id` 恢复，`persist` 在事务中写时间线和会话状态。
- 面经聚合：手动来源先抽取；仅在用户主动开启联网补充时，才进行相关性过滤后的公开面经补搜（使用不同检索意图）→ 汇聚 → Reflection 自校正（反馈驱动重抽取，最多两次）→ 冲突或反思未通过时 interrupt 人工裁决。录入轮次作为材料元数据；岗位级洞察再跨轮次分析全部来源，按语义方向生成高频考察方向、核心问题和准备重点。分析完成后检查该岗位未来固定时间面试，按开始前 24 小时自动同步一条组合准备提醒。
- 岗位问答：先持久化用户问题和“生成中”的 assistant 消息，再由后台 LiteLLM 流式生成并逐段提交；前端轮询增量内容，页面切换或刷新后按岗位历史继续显示，模型不支持流式时自动退回一次性响应。
- 页面恢复：通知录入、面经聚合和备战分析均由服务端查询最近的“运行中”会话；本地会话 ID 丢失或切换页面时，重新进入模块会自动找回，不依赖原页面组件继续挂载。
- 备战分析：上传 PDF/DOCX 简历后，后台读取简历、JD 和已确认面经，生成匹配总结、优势、差距和准备行动清单；新会话不要求可用时间、不创建备战任务或时间线节点，历史已排期数据继续保留。旧会话的 confirm/discard 接口仅用于读取或处理历史待确认状态。

每日巡检不使用 LangGraph：它是固定的本地扫描和一次 AnySearch 查询，应用启动时补跑当天一次，之后在服务器存活期间每天上海时间 09:00 执行；同一天的手动运行会返回既有简报。

第 4 期搜索使用可选的 AnySearch HTTP MCP（最多 5 条结果）和可选用户粘贴。未配置 `ANYSEARCH_API_KEY` 时不会阻塞核心分析，但联网补充、岗位问答公开检索和每日简报公开来源搜索会跳过或记录错误；当前 LiteLLM provider 本身不会自动联网。当前配置下 OpenAI/Anthropic 的联网搜索端点不可用，未保留无法实测的兼容分支；provider 仅用于单来源抽取与 critic。
